## 1. 現況（事實）

### 1.1 去年同期損益表

- 交易池 150 檔全部有官方損益表。最新期別：2026Q3 有 56 檔、2026Q2 有 94 檔（業別：一般業 132、金控 12、銀行保險 4、其他業 1、證券期貨 1）。
- 對照各檔最新期別的去年同期，已有 FinMind 驗證文件（`FINMIND_VERIFIED_PRIOR`）的有 148 檔。**只缺 2 檔**：7828.TWO（2026Q2）與 3718.TWO（2026Q3）。
- 這是今天手動對全交易池跑 `cli/fundamental_repair.py` 之後的狀態。2026-11-10 決策報告裡的「缺去年同期」來自補抓前的 Snapshot；「去年同期由資料商補抓」只是來源限制標籤，不代表缺資料。
- 補抓指令目前只能手動，不在每日排程。它每檔會即時呼叫一次 FinMind（`FundamentalRepairProvider.fetch`），並另建一份研究用 Snapshot。
- 每日流程（`start.sh`）其實已經逐股抓 FinMind `TaiwanStockFinancialStatements`、`TaiwanStockBalanceSheet`、`TaiwanStockCashFlowsStatement` 存成候選（`supplemental_facts`），並在公布區間內每天更新一次（`scripts/finmind_schedule.py`）。缺的只是「把損益表候選核對後轉成去年同期文件」這一步。
- 第三季法定期限是 11/14，官方端點只列已公布的公司；未公布的約 94 檔在期限前後會陸續換成 2026Q3，屆時去年同期又要重補一次。

### 1.2 現金流

- 證交所與櫃買的 OpenAPI 都沒有現金流量表端點，沒有官方數字可當標準答案。
- 現行做法（`data/cash_flow.py`，每日流程已在跑、不連網）：FinMind 現金流量表的累計稅前淨利與官方損益表完全相符才轉成 `cash_flow_statement` 文件，只支援一般業與其他業。
- 目前 132 檔有已核對的現金流文件，其中 50 檔已到 2026Q3、82 檔為 2026Q2。
- 沒有的 18 檔：金控 12、銀行保險 4、證券期貨 1（這三類本來就不支援），以及其他業 1 檔（2207.TW，原因待確認）。
- 已公布 2026Q3 但還沒有 Q3 現金流文件的一般業有 4 檔：2347、2449、3711、6446。
- 所以現金流的實際缺口不大：一般業主要是「剛公布、FinMind 還沒跟上」的時間差。

### 1.4 產業比較

- 現在分析摘要只有上市股的產業代碼（`company_profiles[].industry_code`），`comparison_standard` 固定是 `None`，所以報告普遍寫「未附產業比較標準」。

## 2. A：去年同期補抓排進每日流程

### 2.1 設計

| 項目 | 做法 |
| --- | --- |
| 位置 | `start.sh` 資料階段，放在「FinMind 候選擷取」與「現金流核對」旁邊，成為一個獨立步驟 |
| 選配與關閉 | 已決定預設開啟，可用環境變數關閉（暫名 `PRIOR_REPAIR=0`） |
| 取數方式 | 已決定**不連網**：直接讀每日已存進 `supplemental_facts` 的 FinMind 損益表候選，做法比照 `data/cash_flow.py`。這樣不需要金鑰、沒有額度問題。`supplemental_facts` 是否保存了核對所需的全部欄位（`type`、`origin_name`、單季值、期間）**待確認**；不夠才退回沿用現有的逐檔呼叫 |

| 時間規則 | `available_at` 是實際抓取時間；晚於決策截止時間的資料一律拒絕，不得偽裝成歷史 |
| 產出 | 寫入共用資料庫的 `FINMIND_VERIFIED_PRIOR` 文件，由下一份正式 Snapshot 納入。**不再另建研究用 Snapshot**（那是手動 CLI 的行為，排程不需要） |

### 2.2 金鑰

- 已決定的不連網做法完全不碰金鑰。
- 若需連網，沿用 `start.sh` 現行取得順序：執行環境變數 → 專案根目錄 `.env`（權限 600、Git 忽略）→ macOS 鑰匙圈服務 `etf-agent-finmind`，以 `docker compose run -e FINMIND_TOKEN` 傳入單一步驟。不新增任何會進 repo 的設定。
- 這一步是純 Python 資料程式，不是子 Agent，不經 Agent runner；子 Agent 的 `.env` 拒讀清單與輸出掃描照舊。程式不得把金鑰寫進日誌、警告訊息、manifest 或原始回應存檔（需有測試）。

### 2.3 重跑時點

- 不設固定日期：只要某檔的官方最新期別比它已有的去年同期新，下一次每日流程就補。11/14 前後自然會每天補到新公布的公司。
- 每日 FinMind 候選在公布區間內每天更新，所以官方先出、FinMind 晚一兩天的情況會在之後幾天自動補上；補不到的那幾天該檔維持「不知道」。
- 期限過後仍未公布或補不到的，列入每日資料狀態報告，由人查看。

### 2.4 7828.TWO 與 3718.TWO

- 兩檔都在[基本面缺口補抓](fundamental_data_repair.md)的「確定補不了」名單：7828 缺 2025-03-31 那一期；3718 自 2026-08 才 100% 認列中強光電營收，沒有可比的去年同期（今天的警告是缺 2026-03-31 可比單季營收）。
- 處理：維持不可用，**不推算、不借用其他法律主體的歷史**。排程每天仍會嘗試（成本只是一次本機比對），失敗原因固定列在資料狀態；新一季資料出現時自然重評。
- 對下游的意義：這兩檔的年增率是「不知道」，依 [quality_dip_plan.md](quality_dip_plan.md) 不擋進場也不算通過。

## 3. B：Yahoo Finance 現金流備援

使用者已同意 Yahoo 可作備援來源，並決定**現在只做 B1 的唯讀比對**（第 7 節第 5 項）。以下是日後若要接入（B2）必須遵守的規則；B2 是否做，要等 B1 結果出來後由使用者另行決定。**目前不是已接入的來源。**

### 3.1 來源登記

- 來源代號暫名 `YAHOO_VERIFIED_CASH_FLOW`，文件種類沿用 `cash_flow_statement`。
- 授權：目前 Yahoo 只核准用於研究日線與隔夜指數。財報用途須另外登記 `license_status`、用途範圍、核准日期與核准人；登記位置（Snapshot 文件層級目前如何記錄授權）**待確認**。未登記為 `approved` 前不進正式計算。
- yfinance 是非官方介面，可能限流或改版。

### 3.2 時間與版本

- `available_at` 一律是實際抓取時間；Yahoo 不提供公司發布時間，`published_at` 留空。不回填。
- 每次抓取保存原始回應識別與內容雜湊；Yahoo 之後改寫數字時另存新版本，不覆蓋。

### 3.3 換算

- Yahoo 給單季值，系統用累計值：同一會計年度 Q1 到指定季以 Decimal 加總，缺任一季即拒絕。
- 會計年度非曆年、或 Yahoo 的季末日與官方 `period_end` 對不上：拒絕。
- 單位與幣別：Yahoo 是元、官方是千元。只接受 `financialCurrency` 為 TWD；浮點值先轉成字串再轉 Decimal，換算成千元後必須是整數，否則拒絕。

### 3.4 核對規則（全部通過才納入；任一失敗即拒絕並回報缺口，不填假值）

1. 累計 `Pretax Income` 與官方累計稅前淨利完全相符（與 FinMind 現金流同一個核對基準）。
2. 累計 `Total Revenue` 與官方累計營業收入完全相符（一般業；多一道防線）。
3. 淨利若要使用，只能用 `Net Income Including Noncontrolling Interests` 對官方稅後淨利；`Net Income`（歸屬母公司）不得拿來核對或當作合併淨利。這個欄位對應目前只驗過 2308 一檔，接入前要用多檔確認。
4. 同一期間若已有 FinMind 核對過的現金流文件：以 FinMind 為準，Yahoo 不納入。兩者營業現金流不同時記錄衝突供人查看，不取平均、不擇優。
5. 資本支出缺值：只提供營業現金流，自由現金流標不可用（現行行為）。

已決定維持「完全相符」，不設容差（第 7 節第 6 項）。若 B1 顯示通過率過低，放寬與否須由使用者重新決定，程式不得自行放寬。

### 3.5 範圍

- 只用於一般業與其他業。金控、銀行、保險、證券期貨的現金流不支援，維持不可用（營業現金流對這些業別的意義不同，且沒有可用的核對公式）。
- 限流與失敗：逐檔抓、每次只抓「官方期別比現金流文件新」的股票、設每輪檔數上限；失敗只讓該檔現金流維持缺口，不中斷每日流程。

### 3.6 契約與版本閘門

- 證據種類：`cash_flow_statement` 在 `typed_evidence_v1` 下已對映 `financial`（`decision/input_context.py` 的 `_DOCUMENT_KINDS`），換來源不需要新種類。
- 來源限制說明：`cash_flow_context` 目前寫死「現金流來自 FinMind（非官方）」，Yahoo 文件要有自己的限制說明，並在摘要標明來源。
- 閘門：建議用 bundle 欄位（比照 `fundamental_period_policy`），暫名 `cash_flow_source_policy: finmind_then_yahoo_v1`，**預設不寫＝關閉**。沒有欄位時 `cash_flow_context` 只認 FinMind 文件，即使資料庫裡有 Yahoo 文件也不讀。舊 bundle／舊 run 自帶 Snapshot，逐位元不變。
- `team_inputs` 不升版：現金流摘要不在 `fundamental_metrics` 內，是由 bundle 重算的簡報內容。Finalizer 是否需要對它另做重算比對**待確認**。

## 4. C：產業比較標準

### 4.1 做法

- 分組用**官方產業別名稱**（樣本範圍已決定用全市場，見下一點）：以 t187ap14 的 `產業別` 為準，並與既有 `data/sector_classification.json` 的代碼逐檔對照，建立「代碼 ↔ 名稱」表；對不上的股票不分組。
- 樣本用**全市場同產業公司**，不是只用交易池（交易池內多數產業只有個位數樣本）。t187ap14 每家公司自帶營業收入、營業利益、稅後淨利，可以直接算。
- 交易池內的公司另與已存的官方損益表（t187ap06 系列）逐檔核對這三個數字，不符即該檔不參與、記缺口。

### 4.2 指標與口徑

| 指標 | 定義 | 備註 |
| --- | --- | --- |
| 同產業營業利益率中位數 | 各公司「營業利益 ÷ 營業收入 × 100」的中位數 | 同一年度、同一季別的累計值才放在一起 |
| 該股相對中位數的差 | 該股營業利益率 − 產業中位數 | 只給差值與該股在產業內的名次，不給好壞結論 |
| 樣本資訊 | 樣本數、年度季別、出表日期、是否仍在公布期內 | 必附 |

營收規模、EPS 的產業中位數技術上也算得出來，但跨公司規模差異大、解讀價值低，第一版不做。年增率的產業中位數需要全市場的去年同期資料，目前沒有，不做。

### 4.3 規則

- **最小樣本數**：同產業有效樣本少於門檻時整組不可用。門檻是資料品質常數（建議 5），寫死在版本內，不是策略旋鈕。
- **缺值**：營業收入不為正、營業利益或營業收入缺值的公司不計入；不補值。
- **排除**：金融保險業整組不算（官方損益表沒有可比的營業收入與營業利益，[基本面缺口補抓](fundamental_data_repair.md)「刻意不接入金融業的淨收益」的規則照舊）。其他業、證券期貨等報表格式不同的公司不與一般業混算。
- **公布期內樣本不完整**：期限前只有先公布的公司，中位數會偏。程式要標 `sample_complete: false` 與目前家數；期別混雜（有人 Q2、有人 Q3）時只取同期別，該股自己的期別沒有足夠樣本就不可用。
- **時間**：`available_at` 是抓取時間；`出表日期` 是內容時間（民國日期須轉換驗證）。晚於截止時間的不用。
- Agent 不輸出數字；程式不設「高於中位數多少算好」的門檻。

### 4.4 上櫃端點的確認步驟

1. 對照櫃買中心 OpenAPI 的官方說明，確認 `mopsfin_t187ap14_O` 的資料集名稱、欄位定義與授權。
2. 連續數個交易日抓取，逐檔與已存的上櫃官方損益表（`mopsfin_t187ap06_O_ci`）比對營業收入、營業利益、稅後淨利。
3. 確認產業別名稱與上市的分類是否同一套（名稱相同才合併成一組；否則上市、上櫃分開算）。
4. 已決定確認前先做上市股：上櫃股的產業比較一律不可用；上市股的中位數樣本只含上市公司，要在摘要寫明。

### 4.5 契約與版本閘門

- 產業比較放進 `fundamental_metrics`（程式計算、Finalizer 以 `validate_fundamental_metrics` 整份重算），分析摘要的 `company_profiles[].comparison_standard` 由 `None` 改為帶入結果。
- 閘門：bundle 欄位，暫名 `industry_comparison_policy: official_industry_median_v1`，預設不寫＝關閉；`fundamental_metrics` 版本隨之增加一版。沒有欄位的舊 bundle／舊 run 逐位元不變。`team_inputs` 版本是否需要跟著動**待確認**（取決於 `fundamental_metrics` 的欄位白名單寫法）。
- 證據：每個中位數附所用來源文件的 `evidence_id`。產業層級的數字不屬於單一股票，在 `typed_evidence_v1` 下只能當補充，不能單獨撐起個股主張；個股主張仍須引用該股自己的財報證據。

### 4.6 與 quality_dip_plan 的關係

- [quality_dip_plan.md](quality_dip_plan.md) 第 2.6 節說「相對同產業中位數的估值位置目前做不到」，原因是沒有產業名稱與上櫃分類。本計畫的「代碼 ↔ 名稱」表與上櫃端點確認補的就是這一塊；同產業 PER／PBR 中位數可以共用同一張分組表。
- 估值本身仍走該計畫的來源核對與授權登記，本計畫不處理 PER／PBR 資料。
- 產業比較只會讓「缺產業比較標準」這個缺口消失，不改變該計畫「疑慮不擋、不知道不算通過」的規則，也不構成便宜或貴的結論。

## 6. 測試與文件同步

測試維持 `unittest.TestCase` 風格，涵蓋正常流程與 fail-closed：

- **時間**：抓取時間晚於決策截止即拒絕；時間缺時區拒絕；民國日期格式錯誤拒絕。
- **核對失敗**：官方與 FinMind／Yahoo 金額差一元即拒絕；官方任一項未申報整筆拒絕；缺季、欄位重複、股票誤配、兩個稅後淨利欄位並存一律拒絕。
- **單位與期間**：元／千元換算後非整數拒絕；幣別非 TWD 拒絕；季末日與官方不符拒絕；單季與累計混用拒絕。
- **授權**：來源未登記為 `approved` 時不進正式計算；Yahoo 文件在沒有閘門的 bundle 中不被讀取。
- **來源衝突**：同期間 FinMind 與 Yahoo 並存時只用 FinMind，衝突有紀錄。
- **產業比較**：樣本數不足不可用；金融業不算；期別混雜只取同期別；公布期內標示不完整；交易池公司與官方損益表不符時不參與。
- **降級不中斷**：任一步驟失敗時每日流程照常完成，資料狀態標部分完成。
- **金鑰**：日誌、警告、manifest 與原始回應存檔不含金鑰值。
- **舊 run 不變**：沒有新 bundle 欄位的封存 run 重建雜湊不變。
