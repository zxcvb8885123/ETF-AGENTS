# Token 用量控制：現況說明

## 這是什麼

每天的決策要呼叫很多次 Agent，每次都要餵資料。這份文件說明我們已經用哪些做法減少重複輸入與無效重試，以及哪些想過但沒接入。

原則：能由程式確定的事交給程式，LLM 只處理需要判斷的部分；縮減輸入不能降低研究覆蓋、驗證規則或證據可追溯性。驗證（Validator 與 Guard）一律用原始資料重建，不吃縮減過的版本。

量測單位是送給 Agent 的 `brief_*.json` 檔案大小（bytes），不是 token。

## 已經做的事

| 做法 | 效果與做法 |
| --- | --- |
| 技術面閘門（預設開啟） | 趨勢很一致的股票，技術摘要只附已算好的動能結論，不附逐日歷史；其他附完整歷史。技術 brief 約由 3.57 MB 降到 1.61 MB |
| 分級模型 | Claude CLI 的三位分析師與多空研究員預設用 `sonnet`；交易、現金姿態與風險審查自 2026-10-24 起預設用 `opus`。實測多空用 opus 約 7.3 美元、sonnet 約 2.9 美元；分析師改用 opus 試過一次，事件批次兩次都漏分級而失敗，單批用量約是 sonnet 的兩倍，所以維持 sonnet |
| 交易 brief 去重 | 各批不再重複帶完整帳戶持倉，只帶持股代號與檔數，每批少約 3,176 bytes；逐股持股數、多空論點與引用完整保留 |
| 關閉 MCP 外掛 | Claude CLI 不載入使用者的 MCP 工具；實測一句 `ok` 的固定開銷由約 50,000 降到約 9,700 cache 建立 token |
| brief 精簡格式 | 摘要不縮排、每檔股票一行，仍是合法 JSON；多頭第一批由 138,854 降到 79,040 字元 |
| 事件分析師略過無事件股票 | 查詢視窗內沒有重大訊息（也沒有核准個股新聞）的股票，驗證本來就要求標「未知」，改由程式直接輸出，不送 Agent。以 10/22 資料算，150 檔中有 35 檔被略過 |
| 減少無效重試 | 單股硬上限減碼改由程式處理，不再靠 Agent 修正 |
| 用量記錄 | 每次呼叫的模型、花費與（Claude、OpenCode 的）token 數寫入 `pipeline.json` 的呼叫紀錄 |

重試規則：每個 Agent 任務最多嘗試 2 次；風險修正循環最多 3 次，不放寬。

## 技術面閘門怎麼判斷

- 程式只決定「這檔附完整歷史」還是「只附動能結論」；LLM 仍要對全部交易池給出看多／看空／中性，契約與驗證不變。
- 只附動能結論的條件：資料可用，且收盤同時在 20 日與 60 日均線之上、5／20／60 日報酬皆為正；或同時在兩條均線之下、三段報酬皆為負。
- 資料不足、訊號衝突、欄位缺漏，一律附完整歷史。
- 摘要內會記錄規則版本，以及該批哪些股票只附動能、哪些附完整歷史。
- 這個規則是程式常數，不在 Policy 雜湊內。若將來改成程式直接決定看多／看空，就必須進 Policy 並由 Validator 重算。
- 不想用時，加 `--no-technical-gate`，所有股票都附完整歷史。

### 品質對照（2026-10-20，同 Snapshot 與截止時間，150 檔）

| 分組 | 檔數 | 看多／看空判斷改變 |
| --- | --- | --- |
| 被省略歷史 | 84 | 7（8.3%） |
| 兩輪都附完整歷史 | 66 | 16（24%） |
| 全部 | 150 | 23 |

結論：沒看到閘門造成的差異大於模型自己重跑的變異，但這不等於品質已證實。限制是只有一天、各跑一次，且那 66 檔本來就是訊號衝突的股票。若省略歷史的股票改變比例持續高於重跑變異，就改用 `--no-technical-gate`。

## 常用參數

| 參數 | 預設 | 作用 |
| --- | --- | --- |
| `--technical-gate`／`--no-technical-gate` | 開啟 | 技術面閘門開關 |
| `--analyst-model` | Claude CLI 為 `sonnet` | 只用於技術／基本面／事件分析師；`inherit` 沿用 `--model`；Codex、OpenCode 未指定時沿用 `--model` |
| `--model` | 所選 CLI 的設定 | 多空、交易、現金姿態使用 |

## 怎麼量測

```bash
.venv/bin/python scripts/measure_daily_briefs.py artifacts/<run_dir> [--output 結果.json]
```

- 輸出每份 brief 的大小、股票數、儲存次數與總大小；token 欄位固定為空值。只讀，不修改 run。
- 續跑的呼叫紀錄只含當次新呼叫，不能當整輪費用。
- OpenCode 與 Claude 對新呼叫記錄 token 數；Codex 沒有可靠的用量欄位，不從費用推算 token，也不回填舊 run。

### brief 大小基準（bytes，各三批）

| Brief | 2026-10-19 Codex（全部完整歷史） | 2026-10-20 Claude（開閘門） |
| --- | --- | --- |
| 技術 | 約 1.92／1.89／1.92 MB | 約 0.76／1.03／0.79 MB |
| 事件 | 462,976／696,313／346,167 | 468,556／747,643／354,949 |
| 基本面 | 85,315～96,391 | 92,426／96,391／85,315 |
| 多頭、空頭（各） | 128,012～156,866 | 144,477～167,996 |
| 交易 | 106,325～113,524 | 105,815～117,267 |

事件 brief 不能先篩掉非 high 的事件，因為重大性要由事件分析師判斷。

## 新縮減方案的驗收關卡

1. 雙側基準：相同 Snapshot、截止時間、Policy 與執行器；完整版也要獨立重跑至少一次，比較原版自身的變異。
2. 逐階段 A/B，不一次全縮；統計輸入、追加讀取、重試、輸出與延遲。試驗結果另存，不寫入既有 Decision run。
3. 全部股票、事件與證據編號全量覆蓋；來源授權與可得時間合法；Validator 通過；不新增「未知」。
4. 每個看多／看空與 high／medium 的變動逐條核對；無法證明是可接受的判斷差異，就維持完整輸入。

## 試過但未接入

| 方案 | 輸入降幅 | 品質結果 | 結論 |
| --- | --- | --- | --- |
| 技術 brief 摘要（12 個錨點、極值、近 5 筆） | 約 81% | 驗證全過，但 12 檔判斷改變，兩次試跑彼此有 8 檔不同 | 不接入 |
| 事件內文只留首尾 | 約 17% | 驗證全過，但 21 則重大性改變（含 10 則 high／medium 互換） | 不接入 |

評估腳本是 `scripts/evaluate_technical_brief.py` 與 `scripts/evaluate_event_brief.py`。

## 尚未接入

| 項目 | 原因 |
| --- | --- |
| Codex 用量擷取 | `codex exec --json` 的用量欄位還沒評估與接上 |
| 送交易 Agent 前的預算式提早警示（如持股數貼近上限） | 還沒做；目前由 Guard 在事後拒絕 |
| 增量執行（用每檔輸入雜湊沿用前一日已驗證的分析） | 風險最高：須標明來源 run 與截止時間，雜湊不同一律重跑；暫不接入 |
| 欄位表式編碼、連續視窗與事件原文檢索 | 還沒開始；任何做法都不能篩掉需要分級的事件，衝突時整檔回退完整序列 |
| 外部套件（rank-bm25、LangChain、LlamaIndex） | 專案規則不直接引入，也沒有已驗證能省 token 又維持品質的現成套件 |

## 注意事項

- 摘要只給 Agent 看，不能取代可重算的原始序列；有資料的股票不得因輸入變小被標成「未知」。
- 不把 bytes 換算成確定的 token，也不把 API 快取定價套到訂閱制 CLI。
- 快取只減少重複前綴的成本與延遲，不縮小上下文，也不保證跨獨立 CLI 工作階段命中。
- 股數、現金與權重由程式與 Guard 負責；情境無法符合硬規則時仍然拒絕。
- 修改 Agent 輸入契約時，同步更新[目前每日決策架構](architecture.md)與相關 Skill 的 `references/`。
