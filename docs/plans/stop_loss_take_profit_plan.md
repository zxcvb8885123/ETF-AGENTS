# 停利停損：警示交給交易 Agent，個股崩跌由程式兜底（計畫）

**白話摘要**（2026-11-11）

1. 現在什麼時候會賣：交易 Agent 自己決定賣、帳戶現金低於姿態緩衝時程式減碼、被選為換出者。沒有任何個股層級的強制停損或停利。
2. 會停損嗎：只有「虧超過 15% 的警示」。11-04～11-10 共 5 次警示，交易 Agent 2 次賣（1 檔出場、1 檔減碼）、3 次續抱，事後看五次判斷都不差。
3. 會停利嗎：不會。`gain_alert` 是 null，而且到 11-10 為止沒有任何持股賺超過 5%，停利規則在這段行情一次都不會觸發。
4. 推薦方案 C（混合）：今天只改設定把三個警示門檻填上；之後加「自進場起算」的警示；最後才加一條很寬的程式硬停損，而且只在個股明顯輸給交易池時才動。
5. 不推薦一般的硬停損（8～15%）：在平常行情它只是成本；在連跌尾段抄底的情境，它會把剛買的股票賣在最低點（11-04 進場的候選股，停損 10% 會多虧 9.2 個百分點）。
6. 不推薦程式強制停利：比賽剩 9 個交易日、使用者要吃反彈；11-06 進場的候選股三天平均漲 17%，10% 停利會在半路賣掉。
7. 今天只改設定就能開：`gain_alert 0.10`、`retrace_alert_20d 0.20`、`loss_alert` 由 0.15 改 0.12。程式已支援，警示會出現在交易 Agent 簡報，必須逐一處理。
8. 最可能怎麼虧錢：停損後反彈、與今天開的進攻試單互相抵消、每次來回約 0.8% 的費稅與滑價。
9. 需要使用者決定 8 題，見第 8 節。

狀態：**計畫，未實作、未開啟**。本文件只寫設計，沒有改程式、設定、Policy 或 Skill。文中新名稱（`stop_exit`、`trail_alert` 等）都是暫名。把本文件的行為當成現行行為是錯的。

證據等級：所有數字都是唯讀腳本讀封存檔與 `price_series` 算的算術，沒有驗 manifest 與雜湊，一律 `evidence_grade: replay_reference_only`。它們不是重放，也不是對 LLM 的前瞻驗證；樣本只有一個 120 日行情視窗，進場日彼此重疊、不獨立。

前置閱讀：[`decision-contracts.md`](../decision-contracts.md#持股檢視停損停利)、[`agent_led_offense_plan.md`](agent_led_offense_plan.md)、[`status.md`](../status.md#版本閘門啟用狀態)。

## 1. 目標與非目標

目標：

- 回答「什麼時候會賣、會停利嗎、會停損嗎」，並讓進攻買進的高 beta 股有明確的退場機制。
- 比賽 2026-11-27 結束（使用者 11-11 更正，原記 11-24），剩約 12 個交易日；使用者看短期報酬、要更多操作、願意承擔較大回撤。

非目標：

- 不讓 Agent 輸出任何數字；不放寬 CompetitionGuard；不改帳戶層級的 `drawdown_control`。
- 不做盤中停損。決策每天開盤前跑一次，所有規則都是「收盤確認、隔日開盤執行」。

## 2. 現況

| 賣出途徑 | 誰決定 | 目前設定 |
|---|---|---|
| 交易 Agent 的 `trim`／`exit` | 交易 Agent | 可引用空頭 claim 或持股檢視事實 |
| 虧損警示 `review:<代號>:loss_alert` | 程式標記、交易 Agent 處理 | `loss_alert 0.15`；必須在 `adopted_claim_ids` 處理一次、不可否決，但不是賣出指令 |
| 高點回落警示、獲利警示 | 同上 | `retrace_alert_20d`、`gain_alert` 都是 null，不會出現 |
| 現金低於姿態緩衝的減碼 | 程式（`drawdown_derisk` v5） | 依交易 Agent 的釋出順序賣，單次最多 NAV 的 25% |
| 帳戶回撤 | 程式（`drawdown_control`） | 5% 起回撤下限 neutral、15% 強制防守 |
| 被選為換出者 | 交易 Agent 提名、程式檢查 | 新買進 5 天內不能當換出者 |

程式已支援三個門檻（`src/etf_agent/decision/position_review.py`）：

- `loss_alert`：帳面報酬 ≤ −門檻。
- `gain_alert`：帳面報酬 ≥ 門檻。
- `retrace_alert_20d`：收盤相對近 20 日最高價回落 ≥ 門檻。注意它看的是 20 日高點，不是進場後的高點，所以不是真正的移動停利。

兩個限制：

- 成本在比賽開帳或帳本重建日是當日結算收盤價，不是真實買價。11-05 的持股檢視 25 檔帳面報酬全部是 0，就是重建造成的；任何「自成本起算」的規則在重建日都會歸零。
- 策略反思可以在試用觀察期保護下小幅調整 `loss_alert` 與 `retrace_alert_20d`（門檻不是 null 時）；`gain_alert` 不在可調範圍。

## 4. 反事實算術（`replay_reference_only`）

口徑：開盤進場；每天收盤檢查；觸發後隔日開盤賣出；與「續抱到期末」比較。表內都未扣費稅；賣出一次約 0.54%（手續費 0.1425%＋證交稅 0.3%＋滑價 10bps），來回約 0.8%。

### 4.1 硬停損（自進場價）

「全體差」＝套規則的平均報酬減續抱的平均報酬，單位百分點。

| 情境 | 續抱平均 | 停損 8% | 10% | 12% | 15% |
|---|---|---|---|---|---|
| 實際 10-27 建倉 30 檔 → 11-10 | −7.6% | 觸發 17 檔，−0.4 | 14 檔，−1.2 | 11 檔，−1.8 | 8 檔，−0.9 |
| 11-11 買進候選 25 檔，10-27～10-29 進場、抱 9 日（連跌初段） | −17.2% | 89% 觸發，+5.3 | +3.6 | +1.6 | −2.3 |
| 同上候選，11-04 進場 → 11-10（連跌尾段抄底） | −3.1% | 84% 觸發，−10.6 | −9.2 | −8.2 | −5.0 |
| 同上候選，11-05 進場 → 11-10 | +0.8% | 80% 觸發，−7.8 | −6.3 | −5.3 | −1.3 |
| 交易池 150 檔，整個視窗每日進場、抱 9 日（n=16,724） | +0.1% | 29% 觸發，−0.04 | −0.14 | −0.19 | −0.21 |

- 硬停損只在「連跌剛開始就進場」的情境有幫助。
- 在連跌尾段進場的情境（就是今天開的抄底與試單要做的事），停損幾乎全部觸發，而且賣在反彈前一天。
- 整個視窗平均下來是負的，再扣每次 0.54% 更差。
- 實際持股是低 beta 組合，停損 10% 會賣掉 14 檔，其中 10 檔期末價高於賣價。

### 4.2 只在「個股輸給交易池」時才停損

條件：自進場虧損 ≥ S，且同期報酬比交易池等權差 ≥ R。

| 情境 | 10%／5% | 12%／6% | 15%／8% | 20%／10% |
|---|---|---|---|---|
| 實際 10-27 建倉 30 檔 | 5 檔，+1.0 | 3 檔，+0.9 | 3 檔，+0.7 | 3 檔，+0.5 |
| 候選 25 檔，10-27～10-29 進場 | 60% 觸發，+1.3 | +0.04 | 33% 觸發，−0.6 | −1.1 |
| 候選 25 檔，11-04 進場 | 13 檔，−6.1 | 10 檔，−5.3 | 3 檔，−1.6 | 1 檔，−0.6 |
| 候選 25 檔，11-05 進場 | 2 檔，−1.3 | 1 檔，−0.6 | 0 檔 | 0 檔 |
| 交易池整個視窗 | 20% 觸發，−0.03 | −0.09 | 10% 觸發，−0.11 | −0.12 |

- 加上「輸給交易池」之後，大盤一起跌時不會整批賣出；在實際持股上只賣 3～5 檔，而且賣對了。
- 抄底情境的傷害從 −9 降到 −1.6 個百分點（15%／8%），但沒有消失。
- 它是保險，不是獲利來源：整個視窗平均仍略為負值。

### 4.3 停利、移動停利、時間停損（交易池整個視窗，抱 9 日）

| 規則 | 觸發比例 | 全體差（未扣費稅） | 扣每次 0.54% 後 |
|---|---|---|---|
| 停利 10% | 21% | +0.26 | 約 +0.15 |
| 停利 15% | 12% | +0.15 | 約 +0.08 |
| 停利 20% | 7% | +0.07 | 約 +0.03 |
| 賺 8% 後自高點回落 5% | 13% | +0.03 | 約 −0.04 |
| 賺 10% 後回落 6% | 8% | +0.02 | 約 −0.02 |
| 持有 5 日仍虧就賣 | 64% | +0.22 | 約 −0.13 |

- 只看 25 檔高 beta 候選時，停利 10% 是 +0.09、15% 是 −0.13：高 beta 股的大漲集中在少數幾次，停利會砍掉它們。
- 11-06 進場的候選股到 11-10 平均 +17.1%（最低 +1.5%、最高 +28.7%）；10% 停利會在第二天賣掉大部分。這個視窗後面沒有資料，無法算賣掉之後的結果。
- 時間停損在連跌初段有 +6 個百分點，但在平常行情觸發六成、扣費稅後是負的。

### 4.4 這些數字不能說明什麼

- 只有一個視窗、一次連跌加一次反彈；換一段行情結論可能相反。
- 進場日每天滾動，樣本高度重疊。
- 沒有模擬賣出後現金的去向，也沒有模擬換手上限與整張限制。

## 5. 方案比較

### 方案 A：只填警示門檻，仍由交易 Agent 判斷

- 做法：填 `gain_alert`、`retrace_alert_20d`，視需要調 `loss_alert`；第二步加自進場起算的警示（見 6.2）。
- 優點：今天就能開；不改程式；診斷顯示交易 Agent 處理警示的品質不差；不會賣在洗盤低點。
- 缺點：沒有硬性保證；警示太多會增加交易 Agent 驗證失敗的機會（每個警示都必須剛好處理一次）。

### 方案 B：程式強制出場

- 做法：人填硬停損、移動停利、時間停損的數字，程式確定性賣出，旗標註記、不改寫交易 Agent 的意圖。
- 優點：有保證；不依賴 LLM。
- 缺點：4.1 顯示一般硬停損在這個視窗是負的，而且與今天開的抄底、試單直接衝突；強制停利會砍掉反彈；實作與互動最複雜。

### 方案 C：混合（推薦）

- 警示由交易 Agent 處理（同 A）。
- 程式只兜底一種情況：個股虧損很深，而且明顯輸給交易池（4.2 的條件式停損）。
- 停利與時間停損只做警示，不強制。

| | A | B | C |
|---|---|---|---|
| 今天能開 | 能（只改設定） | 不能 | 第一步能 |
| 連跌尾段抄底被洗出場 | 不會（Agent 判斷） | 會（−5 到 −10 個百分點） | 少（15%／8% 約 −1.6） |
| 個股崩跌有保證出場 | 沒有 | 有 | 有 |
| 砍掉反彈獲利 | 不會 | 會 | 不會 |
| 工期 | 0.5 小時＋4～6 小時 | 12～16 小時 | 0.5＋4～6＋8～12 小時 |

推薦 C 的理由：使用者要吃反彈、願意承擔回撤，所以不該讓程式在大盤一起跌時賣股；但進攻買進的高 beta 股如果自己崩跌，需要一條不靠 LLM 的底線。

## 6. 推薦方案的設計

### 6.1 階段 0：今天只改設定

| 欄位 | 現值 | 建議值 | 依據 |
|---|---|---|---|
| `position_review.gain_alert` | null | `"0.10"` | 11-11 會標到 1 檔（1802）；讓交易 Agent 對賺一成的持股明確表態 |
| `position_review.retrace_alert_20d` | null | `"0.20"` | 近四個決策日各標 3～4 檔；0.15 會標 5～8 檔、0.10 會標 11～12 檔 |
| `position_review.loss_alert` | `"0.15"` | `"0.12"` | 近四個決策日各標 0～3 檔；進攻買進的股票較早被檢視 |

- 開了之後會產生 `review:<代號>:gain_alert`、`review:<代號>:retrace_alert`、`review:<代號>:loss_alert`，交易 Agent 必須在 `adopted_claim_ids` 逐一處理，否則驗證失敗重答。
- 這三個都是警示，不是賣出指令。`loss_alert` 的持股要續抱須同時採納多頭 claim（現行規則）。
- 合計每天約多 4～8 個必須處理的警示。交易 Agent 這一步不可降級，警示越多、用盡修正次數的機會越高，這是填太鬆的主要代價。
- 填了之後，策略反思可以小幅調整 `loss_alert` 與 `retrace_alert_20d`。
- 回滾：三個值改回原值；先存 `config/policy_versions/2026-11-11-before-review-alerts.json`，換新 `policy_id`。

### 6.2 階段 1：自進場起算的警示（`position_review` v2）

`position_review.version: "v2"`（版本閘門，只由人設定）。v1 與沒有欄位的 Policy 逐位元不變。

每檔持股多算四個事實（都由程式算、Finalizer 整份重算）：

- 持有交易日數（取自帳本綁定的 `exposure_rotation.held_since_by_symbol`）。
- 進場後最高收盤相對成本的報酬。
- 目前收盤相對進場後最高收盤的回落。
- 自進場以來相對交易池等權的報酬差。

新增三個人填門檻與對應警示（null＝不啟用）：

| 門檻（暫名） | 警示 | 條件 |
|---|---|---|
| `trail_alert: {arm_gain, giveback}` | `review:<代號>:trail_alert` | 進場後曾賺到 `arm_gain`，之後自高點回落 ≥ `giveback` |
| `relative_loss_alert: {loss, lag}` | `review:<代號>:relative_loss_alert` | 虧損 ≥ `loss` 且輸交易池 ≥ `lag` |
| `stale_alert: {days}` | `review:<代號>:stale_alert` | 持有滿 `days` 個交易日仍為虧損 |

- 交易 Agent 的輸出不變：仍只有意圖、信心列舉與文字，警示用既有的 `adopted_claim_ids` 處理。
- 缺資料（持有起點對不上、行情不足）時該事實為 null、不產生警示，並記入缺口；不補值。
- 帳本重建日成本歸零的問題：v2 的四個事實改用「持有起點之後的行情」算，不依賴 `average_cost`，重建不會讓它們歸零。
- `team_inputs` 不升版、沒有新鍵：`position_review` 自 2.4 起就在 `team_inputs` 內，內容形狀由 Policy 的 `position_review.version` 決定，Finalizer 以同一版本整份重算。2.10 已被 quality_dip 裁決占用，升版會把無關的閘門綁在一起。

### 6.3 階段 2：程式兜底的條件式硬停損（`position_sizing.stop_exit` v1）

人填欄位（全部必填、程式不給預設）：

| 欄位（暫名） | 建議值 | 說明 |
|---|---|---|
| `loss` | `"0.15"` | 自進場的虧損門檻 |
| `lag_to_pool` | `"0.08"` | 同期輸給交易池等權的門檻；兩個條件都成立才觸發 |
| `min_holding_days` | `3` | 持有未滿不觸發，避免剛進場就被洗出 |
| `max_exits_per_run` | `2` | 單日最多強制出場檔數，超過的依虧損由大到小取前幾檔 |

行為：

- 觸發的持股目標股數設為 0，賣單意圖由程式標 `exit`，旗標 `RISK_STOP_EXIT`，說明寫明兩個條件的數值。交易 Agent 的意圖不改寫。
- 前提：`position_review` v2（事實同一份）、`exposure_rotation`（持有起點）。
- 事實算不出來時不強制賣出，留 `STOP_EXIT_UNAVAILABLE` 旗標；該檔仍會有 6.2 的警示，由交易 Agent 判斷。這裡的 fail-closed 是「程式不在缺資料時自動下單」。
- 不需要新的 Agent 輸出，也不需要新的 `team_inputs` 鍵：配置引擎由 bundle 與 Policy 重算，Finalizer 透過既有的配置重建比對。

與其他機制的互動：

| 機制 | 規則 |
|---|---|
| 硬規則（最少檔數、不可交易） | 優先。賣出會讓持股低於 `min_positions`，或該檔當日不可交易時，取消停損並留旗標；Guard 照舊 |
| 換股的 `min_holding_days 5` | 不衝突：那是「不能當換出者」，停損另有自己的 `min_holding_days` |
| `agent_swap` | 觸發停損的持股若同時是提名的換出者，照換股成交（一樣是出場）；停損先於換股判定，不重複賣 |
| `drawdown_derisk` v5 | 停損賣款先計入當日補現金的需求，剩下的才依釋出順序減碼 |
| `exposure_rotation` | 現行設定下不配對（`agent_swap` v2 互斥），無互動 |
| `reentry_cooldown` v3 | 建議停損出場的股票列入提示名單（買回須在 `adopted_claim_ids` 回應），避免隔天原價買回；v3 現行只計交易 Agent 自己的出場，這是要改的地方 |
| quality_dip 梯度、offense 試單 | 不另設豁免；靠 `lag_to_pool` 與 `min_holding_days` 避開大盤一起跌的情況 |
| 換手上限 30% | 停損賣單計入換手，排在買單之前；`turnover_fit` 只會縮買單 |
| 賣款去向 | 停損是單向賣出，不適用「不會只賣不買」。現金高於當日目標的部分回到一般信心預算 |

賣款去向有一個已知問題：2330 目前有 15% 的份額下限，會吸走多出來的現金（見 2026-11-11 審查報告的 A1）。那個問題不修，停損賣款大多會變成加碼 2330。

### 6.4 不做的事

- 程式強制停利、強制移動停利、強制時間停損：只做警示。
- 盤中停損。
- 讓風險 Agent 處理停損停利（現行邊界不變）。

## 9. 風險與反面

- **停損後反彈**：這個視窗最明顯的風險。11-04、11-05 進場的候選股，任何 8～12% 的硬停損都賣在 11-06 低點附近，之後兩天交易池反彈 8%。條件式停損只是降低、沒有消除。
- **與進攻設定互相抵消**：今天開的試單與連跌抄底是「跌深買進」，停損是「跌深賣出」。門檻設得比抄底的進場深度還淺，兩者會在同一週對同一檔股票各做一次。
- **洗盤成本**：每次賣出約 0.54%、來回約 0.8%；單日強制出場 2 檔各 4% 權重，就是 NAV 的 0.04% 成本加上換手額度 8%。
- **警示過多拖垮交易 Agent**：每個警示都必須剛好處理一次；填太鬆會讓交易 Agent 這一步更容易用盡修正次數，整份決策落入備援。
- **賣在大盤低點**：`retrace_alert_20d` 與 `loss_alert` 在連跌時會同時標到很多檔，交易 Agent 可能因為「到處都是警示」而偏向賣出。11-09 的三次續抱事後是對的，但那是三次，不是保證。
- **樣本太小**：所有門檻建議都來自同一段行情。剩下 9 個交易日如果是單邊下跌，寬停損會比窄停損虧得多；如果是震盪，任何停損都只是成本。
- **成本基準**：帳本重建會讓 `average_cost` 歸零，階段 0 的三個警示在重建後幾天會失靈；階段 1 才解決。
