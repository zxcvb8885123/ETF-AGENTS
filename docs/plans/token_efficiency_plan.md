## 1. 結論先講

1. **「快取建立 43%」不是結構性浪費**。實驗確認：每次呼叫共用的固定開頭只有約 3,500 token，而且已經是讀快取；其餘寫入幾乎全是該批專屬的簡報，只寫一次。
   真正重複寫入的共同內容只有 Skill 檔（約占首次 run 寫入量的 5%）與多空兩方相同的簡報（約 8%）。
   **「先跑第一批暖快取」或「調整提示詞順序」在現行流程省不到東西**（第 3 節）。
2. **「快取讀取 49%」是同一次呼叫內分頁讀簡報造成的**，不是跨呼叫共用。Read 工具一次最多回約 2.1 萬 token，簡報被切成多頁，每多讀一頁就把前面全部內容再讀一次。
   實驗確認把上限調高後一次讀完，讀取量少 75%、寫入量不變。這一項按定價只值約 1.5%，但占 token 總數近一半；**若 Max 額度對快取讀取有計入，它是全案最大的一項**（第 4.1 節）。
3. **資料壓縮**：不損失資訊的做法（欄位去重、固定說明只放一次、空值省略）還剩約 $0.7～1.0／run；表格化與縮短編號理論上無損但要 A/B；摘要與便宜模型前處理都會損失資訊或破壞可稽核性，不建議（第 5 節）。
4. **向量索引／向量資料庫不適用於每日決策鏈**。實測 1,654 則公告中內容完全相同的只有 4 則；「相似」的 192 則是同一類公告的不同期別，各自是獨立事實，契約要求每則都分級一次。
   「只送相關的舊公告」就是選擇性取樣，與覆蓋規則衝突，而且現行的跨日沿用已經用確定性雜湊達成同樣目的。建議只列為賽後研究（第 6 節）。
5. **最大的錢仍在重跑與輸出**：每次重跑約 $10～12；輸出只占 token 的 9%，卻占估計金額約四成；重試約占 6%（第 2、7 節）。
6. **11/19 前能上線的**：少開新 run（今天）、一次讀完簡報（1～2 小時，CLI 開關）、量測腳本。其餘排在 11/20 之後或賽後（第 9 節）。

### 2.3 一次典型呼叫的 token 是怎麼來的

以事件分析師為例（11/17 21:17，多數批次：建立 6～9 萬、讀取約 1.9 萬）：

1. 第一個請求：固定開頭（約 1,800～3,500，讀快取；事件分析師因每批 Schema 不同只讀到前段）加上環境資訊與提示詞（約 2,000～4,000，寫入）。
2. Agent 讀 Skill 檔與簡報第一頁（寫入）。
3. Agent 讀 references 與簡報其餘部分（寫入），然後直接輸出結構化結果。

所以簡報只被寫入一次，之後沒有人再讀它。多空與交易的簡報較大，要分 4～5 頁，每多一頁就把之前全部內容再讀一次，讀取量因此是建立量的 2 倍左右。

### 2.4 不知道的事：Max 額度怎麼算

- 官方只說美元是依公開定價算的估計值，沒有說明 Max 額度如何對四類 token 計權。
- API 的文件寫「快取命中不計入速率上限」，但那是 API 的速率上限，**不能直接套到訂閱額度**。
- 這件事決定優先順序：若額度大致按金額比例，重點是建立與輸出；若按 token 數，重點是讀取。
- 建議的校準方法（0 程式碼）：每次 run 開始前與結束後各記一次 Max 用量百分比（`/usage` 或 `claude-dashboard:check-usage`），累積 4～6 個 run 後，對各 run 的建立、讀取、輸出 token 做對照。
  第 4.1 節上線前後各有幾個 run，就能看出讀取量大減時額度有沒有跟著少用。

### 3.2 小實驗（Claude Code 2.1.326、`--model sonnet`、旗標同正式指令、合成文字）

| 實驗 | 第一個請求的讀取／寫入 token | 結論 |
| --- | --- | --- |
| 無附加檔，連續兩次、Schema 相同、提示詞不同 | 第二次：讀 3,478、寫 2,036 | 固定開頭約 3,500 token，**現在就已經跨呼叫讀快取** |
| 同上，提示詞也完全相同 | 讀 5,514、寫 0 | 只有整個第一則訊息逐位元相同才全部命中 |
| `--append-system-prompt-file`（約 12,400 token 的固定文字），連續兩次、提示詞不同 | 第二次：讀 1,809、寫 16,037 | **只加附加檔不會共用**：附加的文字每次都重新寫入 |
| 再加 `--exclude-dynamic-system-prompt-sections` | 第二次：讀 14,892、寫 2,775 | 兩個旗標一起用才共用 |
| 同上，但 Schema 換一個列舉值 | 讀 1,809、寫 15,858 | **Schema 不同，整段重寫**；事件分析師每批 Schema 不同，所以用不了 |
| 兩個呼叫同時啟動（冷快取、內容相同） | 兩個都寫 15,858 | 同時啟動確實都付寫入價；之後再啟動的那個讀 14,892 |
| 讀一個 9.3 萬位元組的檔，預設設定 | 分 2 頁；整次呼叫讀取 36,352、寫入 45,331 | Read 一次只回約 2.1 萬 token |
| 同上，加 `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS=200000` | 1 頁；讀取 9,074、寫入 44,869 | **讀取少 75%，寫入不變** |

另外確認：`result` 事件的 `usage` 是整次呼叫各請求的累計，所以 `pipeline.json` 的 `usage_tokens` 可以直接拿來前後對照。

限制：每種情況只跑一次、文字很短、只測 sonnet；附加檔相對於快取斷點的位置官方沒有寫，換 CLI 版本可能不同。

官方文件的對應說法（2026-11-17 查閱）：

- 快取前綴依 `tools`、`system`、`messages` 的順序建立，前面一層有變動，後面全部失效；工具定義改變會讓整個快取失效。
- 同時送出的請求，快取要等第一個回應開始後才可讀；要讓平行請求命中，須等第一個回應開始再送其餘的。
- Claude Code 的說法：同一目錄平行執行的 session 會建立相同前綴、可互讀；先後執行的 session 只有啟動時的 git 狀態快照相同才共用。訂閱方案內 `-p` 的主對話預設 1 小時 TTL（本專案已改 5 分鐘）。
- 來源：<https://platform.claude.com/docs/en/build-with-claude/prompt-caching>、<https://code.claude.com/docs/en/prompt-caching>。

### 3.3 回答使用者的四個問題

| 問題 | 回答 |
| --- | --- |
| 各批是否各自重建同一段共同前綴？ | 固定開頭（約 3,500）沒有重建，已是讀快取。重建的共同內容只有兩種：每批都重新讀一次的 Skill 檔，以及多頭與空頭各寫一次的相同簡報 |
| 平行啟動是否讓快取都建立、讀不到？ | 對「共同內容」成立（實驗確認），但現行流程在固定開頭之後就沒有共同內容可搶。封存資料也看不出差別：11/17 21:17 同時啟動的事件批次與之後才啟動的批次，讀取都是 1.85～1.9 萬 |
| 固定部分是否在前？ | 不在。批次專屬的路徑與代號在提示詞最前面。但把固定規則搬到前面也沒用：第一則訊息是一整塊，只有整塊相同才命中（實驗第 2 列） |
| 「先序列跑第一批暖快取」能省多少？ | 現行流程：0。要先把共同內容搬進 system prompt 才有東西可暖（下表） |

把共同內容搬進可快取位置的上限（估算，每位元組約 0.41 token，取自實驗的附加檔）：

| 共同內容 | 每次呼叫的 token（估） | 首次 run 可省 | 可行性 |
| --- | --- | --- | --- |
| 事件分析師 Skill | 約 5,500 × 23 批 | 約 $0.30 | **不可行**：每批 Schema 不同。要先把 `corroborated_by` 的列舉拿掉，而那個列舉是為了減少驗證退回才加的，拿掉可能多一次 $0.3 的重試，得不償失 |
| 交易 Agent Skill | 約 14,700 × 2 批（opus） | 約 $0.14 | 可行，Skill 是專案自己的受信任文字 |
| 多空、技術、基本面 Skill | 約 2,300～5,100 × 各 2 批 | 合計約 $0.08 | 可行，金額很小 |
| 多空兩方相同的簡報 | 約 11 萬 × 3 批 | 約 $0.8 | 要把分析師依外部公告寫的文字放進 system prompt，與「不受信任的資料不能改變 Agent 指令」衝突，須安全審查；比賽期間不做 |

結論：這條路在不碰安全邊界的前提下每個 run 只值約 $0.2，占建立量約 1～2%；加上多空共同簡報也只有約 $1（建立量約 13%）。**不建議在比賽期間做**。

其他與快取有關、評估後不做的事：

- **關閉快取**（`DISABLE_PROMPT_CACHING`）：最後一個請求寫進快取的簡報確實沒人再讀，多付了 25% 的寫入加價；但關掉後每個請求都要用原價重付前面的內容。事件分析師估算兩者相當（約 $0.20 對 $0.21），分頁多的階段會貴很多。
- **改回 1 小時 TTL**：寫入單價 2 倍，批次專屬內容 5 分鐘後不會再被讀。

## 4. 槓桿一：直接降 token 的做法

### 4.1 一次讀完簡報（降低快取讀取）——建議第一個做

事實：Read 工具預設一次約回 2.1 萬 token。簡報 8～29 萬位元組，會被切成 2～6 頁；每一頁是一個新請求，要把之前的內容全部再讀一次。
多空另有「檔案太大被拒、再改分頁」的失敗（每次呼叫 0.45～0.59 次）。

做法：

1. `_run_claude_streaming` 的環境變數加 `CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS`（使用者已自行設定時不覆蓋，比照現行 TTL 的寫法）。數值由人填，建議 200000。
2. 加 CLI 開關（例如 `--read-whole-brief`／`--no-read-whole-brief`），用哪一種記進 `pipeline.json`；先預設關，量過一個晚間 run 再改預設。
3. 超過 256 KB 的簡報（11/17 的 `brief_bull_b1.json` 287 KB、新聞標註 292 KB）Read 會直接拒絕。兩種處理擇一：
   程式把這類簡報拆成兩個檔（各自小於 256 KB、內容逐值不變、提示詞列出兩個路徑），或維持現狀讓它分頁。這一點**沒有實測**，上線前要用真實簡報試一次。

| 項目 | 估算 |
| --- | --- |
| 讀取 token | 少 60～80%。以 21 個 run 推算：59.6M 降到約 12～24M，等於 token 總數少 30～38% |
| 建立與輸出 token | 不變 |
| 估計金額 | 每個 run 約少 $0.2～0.3（1.5%） |
| 其他好處 | 每次呼叫少 2～4 個來回，較快；讀檔失敗變少 |

- 品質風險：低。Agent 看到的內容完全相同，只是一次拿到。事件分析師多數批次本來就是這樣讀的。
  要注意的是單一工具結果變得很長（多空一批約 11～13 萬 token），是否影響判讀沒有量過，用第 8 節的方法對照。
- 版本閘門：不需要。簡報內容與雜湊都不變，Validator 與 Finalizer 不讀簡報。只是執行設定，CLI 開關即可。
- 只適用 Claude runner；Codex 與 OpenCode 不受影響。
- **值不值得，取決於 Max 額度是否計入快取讀取**（第 2.4 節）。它成本低、風險低，而且上線前後的對照正好用來回答那個問題，所以排第一。
- 檔案：`src/etf_agent/automation/agent_runner.py`、`scripts/run_daily_pipeline.py`、`tests/automation/` 對應測試、`docs/token_usage.md`。

### 4.2 少開新 run（0 程式碼）

沿用 [`event_analyst_token_reduction_plan.md`](event_analyst_token_reduction_plan.md) 第 9 節：失敗後用 `--resume` 續跑、重跑前先看失敗原因、排程的 21:00 與 07:00 之外不再手動另開。

- 每避免一次重跑省 $10～12，比本計畫任何一項程式改動都多。
- 過去 7 個目標交易日有 2 個白花的 run（$28.7）；其中 3 個目標日各有 3 次實際花費的 run。

### 4.3 驗證失敗只重做失敗的股票

- 品質風險：低，沒出錯的股票不會因重試被改寫。
- 版本閘門：不需要；重試上限與 fail-closed 不變。

### 4.6 模型分級與階段合併

- 交易、排序、提名、現金姿態、風險審查維持 opus；多空維持 sonnet（理由見 `token_cost_reduction_plan.md` 4.8）。
- 新聞逐則標註與技術分析師可以用 haiku 做**影子比對**（多跑一份、不進決策）。比賽剩 8 個交易日，累積不到 10 個決策日的樣本，所以比賽期間不切換。
- **不合併分析師階段**：三位分析師的簡報內容不重疊，合併只省每批約 6,000 token 的固定開銷（約 $0.1），卻會讓單一輸入變長、失敗時一起重做。
- **不合併多空**：破壞隔離。

## 5. 「資料壓縮」逐項評估

| 含義 | 是否損失資訊 | 可行性 | 預估省／run | 結論 |
| --- | --- | --- | --- | --- |
| 欄位精簡與去重（固定說明只放一次、空值省略、同一事實只留一份） | **不損失**，程式可還原 | 高。已做一部分；剩事件的 `financial_context`、多空的 `evidence_kinds`、基本面的固定說明 | $0.7～1.0 | 可做，11/20 之後 |
| 交易簡報的 `dip`（占 39%）省略空清單與 false | **不損失** | 高，但那是最後整合關、最貴的模型 | $0.15～0.3 | 可做，保守處理 |
| 表格化（表頭一次、每列只有值） | 資訊不損失，但模型判讀是否一樣好沒有驗證 | 中。技術的 `trend_history` 占技術簡報約三分之二 | $0.1～0.4 | 要 A/B，賽後 |
| 多空簡報的 low 事件只給索引 | **損失可見範圍** | 中。多空簡報 79% 是 `analysts`，其中 low 事件約兩成 | $0.45 | 每個 run 約 2 個只靠 low 事件的空頭論點可能消失；賽後 |
| 縮短證據編號 | 資訊不損失（程式對回原編號） | 低。編號平均只有 14～15 字元（例如 `document:4057`）；多空簡報裡編號占 19.7% 字元，主因是 `evidence_kinds` 重複列一次，上面第一列已涵蓋 | $0.1～0.2 | 不做：多一層對照表，引用錯誤的風險大於好處 |
| 摘要預處理由程式做 | 看做法：結構化抽取（已做）找回了被截掉的內容；只留首尾（試過）改變 21 則重大性 | 已做完能做的部分 | — | 不再往下做 |
| 便宜模型先做摘要再給主模型 | **損失**，而且摘要無法由 Validator 重算 | 低 | 不估 | 不做（見下） |
| LLMLingua 類有損壓縮 | **損失**，會改寫數字與編號 | 不可行 | — | 不做 |

「便宜模型做前處理」不做的理由：

1. 摘要是 LLM 產物，夾在 Snapshot 與分析師之間，主張就不再能直接追溯到原始證據；Validator 只能驗編號存在，驗不了摘要有沒有漏掉關鍵數字。
2. 等於多一個要驗證、要封存、要計入額度的階段。haiku 的提示超過 10 萬 token 時單價變 5 倍。
3. 事件跨日沿用已經讓多數舊公告不必重送，剩下的是真的新公告，沒有理由再壓。

**不損失資訊的壓縮全部做完約 $0.9～1.3／run**，與使用者量到的「簡報瘦身全部加總約 $2／run（約 10%）」一致，其餘是會改變 Agent 可見範圍的項目。

## 6. 向量索引／向量資料庫（RAG）適不適用

### 6.1 逐項對照專案規則

| 規則 | 與向量檢索的關係 |
| --- | --- |
| 每則重大訊息與新聞都要剛好分級一次；情緒標籤必須覆蓋視窗內全部項目、不能選擇性取樣 | **直接衝突**。檢索的本質就是「只挑最相關的幾則」。沒被挑到的公告不是沒有，是沒被看到 |
| 事件簡報不能先篩掉非 high 的事件，因為重大性要由事件分析師判斷 | 用相似度決定送不送，等於讓嵌入模型先做了重大性判斷 |
| Agent 不得自行檢索，只讀本次提供的 Skill 與簡報 | Agent 端的 RAG 不可行；只剩程式端的前處理 |
| 數字由確定性工具計算、Validator 重算；資料時間以 `available_at` 判斷 | 程式端可以做到 point-in-time（只索引 cutoff 前可得的文件）；但重算需要「同一個嵌入模型、同一版本、同一硬體下逐位元相同」，浮點運算與模型版本都要釘死並封存 |
| 不在專案內直接串模型 API | 雲端嵌入 API 不能用。本機嵌入模型要新增 torch 或 onnxruntime 一類的相依，改 `requirements.lock`、重建 Docker 映像 |
| 來源須 `license_status=approved`、外部文字不受信任 | 嵌入本身不違反，但索引要保存文件版本、來源與可得時間，等於再做一套版本化儲存 |

### 6.2 兩個具體用途

**(a) 公告去重／相似公告聚類（程式端）**

實測 11/17 21:17 的事件簡報（1,654 則）：

| 項目 | 數字 |
| --- | --- |
| 同一檔股票、正文完全相同 | 4 則 |
| 同一檔股票、標題去掉數字與日期後相同 | 93 組，多出來的 192 則（占則數 11.6%、正文字元 14.2%） |

- 完全重複幾乎不存在，去重沒有東西可省；而且完全重複用內容雜湊就能找到，不需要向量。
- 那 192 則是同一類公告的不同期別（例如每月的背書保證、取得有價證券），數字各不相同，各自是獨立事實，契約要求各分級一次。把它們聚成一群只送代表，就是選擇性取樣。
- 真正的「同一則公告隔天又出現」已經由跨日逐檔沿用處理：用逐檔簡報列的雜湊判斷，確定性、可稽核、fail-closed。向量相似度在這裡只會更模糊。
- 若將來要做「同類公告合併呈現」（表頭一次、各期一列），用標題正規化的確定性規則就夠，不需要嵌入。

**(b) 只把與今日決策相關的舊公告送給 Agent**

- 「相關」沒有可驗證的定義。重大性正是事件分析師要判斷的東西，用相似度預先篩選是把判斷交給一個不能稽核的模型。
- 與 quality_dip 的牽動同 `event_analyst_token_reduction_plan.md` 4.3：舊的 high 負面事件若沒被檢索到，股票可能從「有新壞事」變成換股候選，屬於加風險方向。
- 使用者真正要的效果是「舊公告不要每天重付」。這件事跨日沿用已經做到（112／149 檔），下一步是逐則沿用（該計畫的方案 2），兩者都不需要向量。

### 6.3 嵌入的非確定性與稽核

- 同一段文字在不同版本的嵌入模型、不同硬體或不同執行緒設定下，向量可能有末位差異；近似最近鄰索引的結果還跟建索引的順序有關。
- 要符合「可重算」，得封存模型檔雜湊、用精確搜尋、固定排序的決勝規則，並在 Finalizer 重算比對。這是一整個新的契約與版本閘門。
- 稽核時要能回答「這則公告當天為什麼沒有送給 Agent」。雜湊比對可以回答（內容相同或不同）；相似度 0.83 對 0.81 回答不了。

### 6.4 相依、時程與結論

| 項目 | 估計 |
| --- | --- |
| 新相依 | 本機嵌入模型與推論套件（數百 MB 到數 GB）、向量索引套件；改 lock、Docker、CI |
| 新契約 | 索引的版本化與封存、嵌入模型版本閘門、Finalizer 重算、策略反思禁區 |
| 工作量 | 至少 3～5 天，不含 A/B |
| 能省多少 | 事件沿用上線後，事件分析師剩約 $3～4／首次 run；向量方案最多再省其中一部分，而且要付出覆蓋規則 |
| 比賽剩餘 | 8 個交易日，累積不到 10 個決策日的驗證樣本 |

**結論：不在剩下 8 個交易日內做，也不建議賽後接進每日決策鏈。** 可以當論文或賽後的獨立研究，而且只做離線分析、不影響決策，例如：

- 用嵌入對封存的公告做聚類，檢查事件分析師對同一群公告的重大性分級是否一致（評測用途，不是輸入篩選）。
- 比較「確定性標題正規化」與「向量聚類」找出的同類公告有多少重疊，作為「為什麼本系統不用 RAG」的實證。

這兩項都是旁觀者性質，不得被 `decision/`、`automation/` 匯入，結果標 `evidence_grade: replay_reference_only`。

## 8. 怎麼量出真的省了

資料來源一律是 `pipeline.json` 的 `agent_calls[].usage_tokens`（`cache_creation_input_tokens`、`cached_input_tokens`、`output_tokens`）與 `estimated_usage_usd`；讀檔次數取自 `var/logs/agent_trace/<run>/*.jsonl`。

   驗收：對本文件第 2.2 節的兩個 run 算出相同數字。
2. **不同天的資料量不同，所以比「比率」不比絕對值**：

| 槓桿 | 對照指標 | 基準（11/10～11/18） | 通過條件 |
| --- | --- | --- | --- |
| 一次讀完簡報 | 各階段「讀取 ÷ 建立」；每次呼叫讀簡報次數 | 多頭 2.0、空頭 1.8、交易 1.7、技術 1.1、基本面 1.3、事件 0.5；讀簡報 5.4／4.2／3.7／3.2／3.3／2.3 次 | 多空與交易的比率降到 0.5 以下、讀簡報次數降到 2 以下；「建立 ÷ 簡報位元組」變動在 ±10% 內；重試次數不增加 |
| 失敗只重做失敗股票 | 重試金額占比；重試那次的建立 token | 6.0%；與第一次相同 | 占比降到 3% 以下 |
| 技術同日沿用 | 重跑時技術分析師的呼叫數與金額 | 3 次、$0.83～1.16 | 與沿用檔數成比例下降 |

3. **品質對照**：沿用 `token_usage.md` 的驗收關卡與 `token_cost_reduction_plan.md` 第 7 節。第 2 項（一次讀完）不改內容，最低限度的檢查是：
   上線後第一個 run 的驗證退回率、`unknown` 數、多空 `strength` 分布與交易 `intent` 分布，與前三個 run 的範圍相比沒有異常；有異常就關開關。

5. 所有回放與重算標 `replay_reference_only`；能證明的是「token 真的少了、驗證沒有變差」，不能證明決策品質不變。

每一步照 AGENTS.md 跑完整 pytest、`compileall` 與 `git diff --check`；改到執行參數或簡報格式時同步更新 `docs/token_usage.md`、`docs/architecture.md` 與 `src/etf_agent/automation/README.md`。
簡報格式換版的那一次，事件逐檔雜湊會全部不同而全數重判（多花一次約 $8），要選在晚間首次 run 之前上線。

## 10. 不建議做的事

| 項目 | 原因 |
| --- | --- |
| 先序列跑第一批暖快取、其餘再平行 | 現行流程沒有共同內容可暖，省 0，還拖慢交件 |
| 調整提示詞順序（固定規則放前面） | 第一則訊息整塊相同才命中，實驗確認無效 |
| 降低 `--max-workers` | 不省 token，只會變慢 |
| 只加 `--append-system-prompt-file` | 實驗確認不共用，每次重寫 |
| 關閉快取、改回 1 小時 TTL | 見第 3.3 節 |
| 便宜模型先摘要、LLMLingua 類壓縮 | 損失資訊、無法重算 |
| 縮短證據編號 | 省得少，多一層對照表 |
| 合併分析師階段、合併多空 | 省約 $0.1 或破壞隔離 |
| 縮短公告回溯期到 14 天 | 會改變 quality_dip 的新壞事判斷，屬加風險方向（見事件計畫 4.3） |
| 向量索引／向量資料庫接進每日鏈 | 與全量覆蓋、可稽核、不串模型 API 的規則衝突，時程也不夠 |
| 比賽期間切換 haiku 或降 effort | 樣本不足以驗證 |

## 11. 要使用者決定的三題

1. **是否先上線「一次讀完簡報」並同時做 Max 用量校準？**
   推薦：是。它不改 Agent 看到的內容、可隨時關，而且是唯一能回答「Max 額度到底看 token 數還是看金額」的對照。讀取上限建議填 200000；超過 256 KB 的簡報先維持分頁，不拆檔。
2. **重跑怎麼管？**（**已決定，2026-11-17：照推薦執行**，規則已寫進 [`../operations.md`](../operations.md) 的「撞到用量上限或需要重跑」）
   推薦：保留 21:00 與 07:00 兩次排程；其餘一律先 `--resume`，只有續跑也失敗才另開新 run；已有 approved 決策且沒有新的重大資訊時不再手動重跑。這一項不用寫程式，省得最多。
3. **向量索引與其他會改變 Agent 可見範圍的壓縮（表格化、low 事件索引、haiku、effort）是否全部留到賽後？**
   推薦：是。比賽期間只做第 7 節第 1～5 項；第 6、7 項等第 1 題的校準結果出來、確認額度仍然吃緊再做。向量索引只做賽後的離線研究，不接進決策鏈。

## 12. 沒有確認的事

- Max 額度對四類 token 的計權方式（第 2.4 節）。
- 超過 256 KB 的檔案在調高讀取上限後是否仍被拒絕；多空一批約 11～13 萬 token 的單一工具結果對判讀有沒有影響。
- 實驗只跑 sonnet、每種情況一次、文字很短；opus 與真實大小的簡報可能不同。`--exclude-dynamic-system-prompt-sections` 搭配附加檔能共用是實驗觀察，官方文件沒有寫明。
- 真實呼叫的請求數是由 `agent_trace` 的事件順序推斷的，trace 沒有存逐請求的用量。
- 每位元組 0.41 token 取自合成的中文規則文字，套到 Skill 檔只是近似。
- 技術分析師同日沿用的「88／150 同輸入」是使用者的量測，本計畫沒有重算；基本面證據編號為何每次不同也沒有查。
- 第 5 節各項金額沿用既有三份計畫的估算，事件跨日沿用上線後會變小，要用第一個新口徑的 run 重算。
