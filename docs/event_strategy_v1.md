# 事件策略 V1

## 1. 目標與範圍

本文件定義策略層目前優先開發的事件功能：在 2026 年 10 月 26 日至 11 月 27 日的 24 個交易日初賽中，從官方 150 檔交易池找出可在比賽期間內反映的事件型機會。

事件模組輸出可追溯的事件候選清單與分數。下一個策略階段會接入動能，將候選分成進攻股與防守股；之後再交給風控與買賣模組建立交易。完整開發流程見 [Agent 開發架構](agent_plan.md)。

每個候選必須只使用當日 08:55 前已公開、已取得的資訊；資料來源、發布時間與原始證據都要保存。交易規則仍以官方規則為邊界：只限官方 150 檔台股現股、不得放空，且最終組合要符合持股檔數、現金與個股上限。

## 2. 本版流程

```text
官方 150 檔交易池 + 事件日曆 + 公司／總體公告 + 前一交易日日價量
  → 驗證來源、股票代碼與發布時間
  → 建立 EventSnapshot
  → 事件評分與價格確認
  → 輸出排序後的 EventCandidate 清單與理由
```

## 3. 資料需求與證據契約

每一筆事件資料都要轉成同一個結構，不能只保留摘要文字。

| 欄位 | 說明 |
| --- | --- |
| `symbol` | 官方交易池股票代碼；總體事件可為空，影響到個股時才建立關聯 |
| `event_type` | 月營收、季報、法說會、MSCI、公司重大訊息或總體事件 |
| `published_at` | 原始資料首次公開時間，必須有 Asia/Taipei 時區 |
| `catalyst_date` | 預定公告日或實際發生日 |
| `source_url` | 可回查的官方公告或原始來源連結 |
| `evidence` | 原始數字、比較基準與必要上下文，不以模型摘要取代 |
| `direction` | 利多、利空或待確認；待確認不得直接進入候選 |
| `fetched_at` | 本系統取得時間 |

`EventSnapshot` 要有 `run_id`、`decision_cutoff`、交易池版本、包含的事件 ID、當時使用的日價量資料日期與品質旗標。事件在截止時間後發布，必須留到下一個可決策日，不能回填到先前快照。

## 4. 事件來源與判定

第一版只追蹤可核對的事件：

1. **月營收**：10 月與 11 月公告的單月營收、年增／月增與最近三個月累計趨勢。
2. **第三季財報與法說會**：營收、毛利率、EPS、公司展望與法說會重點，必須有公告時間。
3. **MSCI 11 月審查**：新增、刪除與權重調整的正式公告。
4. **公司正式重大訊息**：重大訂單、產能、資本支出、處分、併購及可直接連到營收或獲利的政策事件。
5. **總體事件**：FOMC、CPI、就業報告等會改變台股風險偏好的事件；只有能連結到交易池股票或產業時才納入候選理由。

社群傳聞、沒有原始連結的新聞轉述、沒有日期的長期題材與無法確認數字的「優於預期」不得成為訊號。缺少市場一致預期時，只描述同比、環比與趨勢，不判定是否優於預期。

## 5. 事件評分與價格確認

每個事件候選以 100 分評分，再扣除最高 25 分風險分。

| 分項 | 分數 | 判斷內容 |
| --- | ---: | --- |
| 事件時效 | 15 | 已發生或 10 個交易日內發生，且在比賽結束前有足夠反應時間 |
| 基本面變化 | 25 | 月營收加速、獲利品質改善、毛利率改善或上調展望 |
| 價格確認 | 30 | 公告後相對交易池走強、收盤位置健康且成交量增加 |
| 延續可能 | 15 | 影響可延續數週，非一次性會計收益 |
| 流動性 | 10 | 有足夠成交量，沒有明顯無量漲跌停或價格失真 |
| 證據品質 | 5 | 來源、時間、數字與比較基準完整 |

風險扣分包含公告前急漲、公告後已過度反應、一次性收益、資料互相矛盾與價格無法合理成交。65 分才進候選池，75 分才標為優先檢視。

事件公布後，價格確認至少符合以下三項中的兩項：

- 最近一個完整交易日報酬高於交易池等權重報酬。
- 收盤位於當日價格區間上半部。
- 成交量高於過去 20 日中位數的 1.5 倍。

公告在收盤後發布時，下一次決策才使用；公告在 08:55 前發布但尚未經過完整交易日驗證時，候選標示為「待價格確認」，不列優先檢視。事件後股價已上漲超過過去 20 日平均真實波幅的三倍，標示為「暫停追價」。

## 6. 候選清單輸出

每次執行輸出依分數排序的 `EventCandidate`，至少包含：

| 欄位 | 說明 |
| --- | --- |
| 股票與事件類型 | 指出候選標的及其催化來源 |
| 分數與風險扣分 | 保留每個分項，不只給總分 |
| 價格確認 | 三項條件各自的結果與資料日期 |
| 時間判斷 | 公布時間、預計反映時間、距比賽結束天數 |
| 證據 | 原始來源連結、事件 ID 與引用數字 |
| 狀態 | 優先檢視、待價格確認、暫停追價或淘汰，並附理由 |

同一家公司有多個事件時先保留各自的事件卡，再依證據是否支持同一方向合併總分；資料衝突時標示衝突，不自行取較有利的解讀。

## 7. 執行節奏

1. 盤後更新日價量、公司公告與事件日曆。
2. 在下一個交易日 08:55 前固定 `decision_cutoff`，只讀取截止時間前的資料。
3. 建立 EventSnapshot，淘汰股票代碼不在官方交易池、來源不可回查或時間不完整的事件。
4. 計算事件分數、風險扣分與價格確認，輸出候選清單。
5. 保存快照、候選結果與原始證據，讓同一筆決策能重播與檢查。

## 8. 回測測試計畫

回測以每日 08:55 的 `decision_cutoff` 重建當時可取得的 `EventSnapshot`，依交易日順序重播策略。任何截止時間後發布或系統尚未取得的事件，只能從下一個決策日開始使用，不得以事後資料回填。

第一階段先建立可重現的策略重播測試：使用固定交易池、事件快照、價格特徵與市場狀態，逐日產生候選及目標權重；相同輸入重播兩次必須得到完全一致的結果。測試至少涵蓋截止時間前後發布、證據缺漏、價格確認成立與失敗，以及多空市場狀態切換。

接入買賣與風控模組後，再加入完整交易回測，納入下一交易時段成交價、交易成本、停損、確認失敗、時間停損與最長 10 個交易日持有期限。不得使用當日決策後才知道的收盤價作為成交價。

回測報告至少輸出累積報酬、最大回撤、勝率、平均持有天數、換手率、現金比率、事件類型與市場狀態分組績效，並與交易池等權重基準比較。驗收時同時檢查持股 25 檔、不得放空、個股與產業上限、資產權重合計為 1，以及每筆交易可回查到當時快照與證據。

## 9. 現況與下一步

目前已有官方 150 檔交易池、兩年日價量、原始行情保存、資料庫與價格特徵。尚未接入月營收、季報／法說、MSCI、公司重大訊息與總體日曆，因此目前只能產生價格預篩，不能產生真實事件候選。

下一個實作工作依序為：先建立事件資料表與 EventSnapshot 契約，再接入月營收與公司公告，最後實作事件評分與候選清單輸出。事件模組完成後，依開發架構接入動能、進攻／防守分類、風控買賣與報告。
