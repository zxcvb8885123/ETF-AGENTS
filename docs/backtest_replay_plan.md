# 回測重放計畫：用歷史時點重跑完整決策鏈

> 建立於 2026-09-29（Asia/Taipei）。目標：拿目前的每日決策鏈（分析團隊 → 重大事件研究 → 多空研究 → 交易 → 風險 → Guard），在過去某個交易日 08:55 只使用當時可得的資料重跑，照比賽規則成交並估值，回答「這套架構可不可行」。本計畫取代 [每日自動化與回測就緒計畫](automation_backtest_readiness_plan.md) 中「比賽前不做 Agent 歷史重跑（C3）」的決定。

## 目標與非目標

- 目標：驗證架構端到端可行（能跑完、Guard 不誤擋、委託合理）、估算耗時與 Agent 呼叫成本、初步觀察扣除成本後的績效與相對基準的差異。
- 非目標：不證明策略有效。21 個交易日、單一市況、LLM 每次輸出不同，結果固定標示 `evidence_status=insufficient`，不可當作實盤或送件依據。
- 不修改正式資料庫、正式虛擬帳本與正式封存；不自動下單。

## 參考：TradingAgents 的做法與取捨

來源：<https://github.com/TauricResearch/TradingAgents>（README 說明的介面，未逐行審閱其程式）。

| 做法 | 本計畫的取捨 |
| --- | --- |
| 同一套 Agent，只把分析日期換成歷史日期 | 採用：直接呼叫 `DailyDecisionPipeline`，不另寫回測專用 Agent |
| 只提供分析日以前已發布的資料，財報以當時已申報為準 | 採用：以 `available_at` 篩選，見下節 |
| 依日期網格批次執行、失敗可續跑 | 採用：沿用 `--resume`，每個交易日一個獨立 run 目錄 |
| 以超額報酬評分 | 採用：與 0050、加權指數及不用 LLM 的規則策略比較 |
| 把過去決策結果寫入記憶回饋給下一次 | **不採用**。回測中回饋後續結果等同使用未來資訊；Agent 每日只能看到當時已存在的封存 |

## 設計

### 隔離

- 使用 `var/backtest.db`（由正式資料庫複製）、`artifacts/backtest_runs/<backtest_id>/` 與獨立帳本 `backtest-<id>`；程式路徑不得寫入正式路徑，Docker／CLI 以參數強制指定。
- 預設實作位置：先放本專案 `src/etf_agent/backtest/replay/`（需直接重用 `DailyDecisionPipeline`、`TradingCalendar`、`ExecutionSimulator`）；之後可抽出成獨立 repo，依賴方向維持「回測 → 決策鏈」單向。

### 歷史時鐘與 `available_at`

- 每個交易日 `decision_cutoff = 該日 08:55 +08:00`，由 `TradingCalendar` 產生；休市日不執行。
- 不改寫既有列的 `fetched_at`。回測資料庫另建**重建的可得時間**欄位或視圖，`available_at` 依來源規則推導並標記 `availability_basis=reconstructed`：
  - 日線：該交易日 14:30 收盤後；官方日成交資訊公布時間需以來源確認，保守取 18:00，前一日資料才能進入次日 08:55 的 Snapshot。
  - 月營收與重大訊息：使用公告本身的發布時間；無時間者一律排除。
  - 財報：使用實際申報日 00:00 起，缺申報日者排除。
- 使用 Snapshot 時，回測模式改以重建的 `available_at` 篩選，而非 `fetched_at`；Snapshot 需記錄使用的篩選模式，Validator 拒絕混用。
- Yahoo 事後補抓的資料只可作備援且需標示；優先用官方來源。

### 交易狀態

- 歷史處置／暫停交易資料補不到的日期，交易狀態包標為 `backtest_assumed`，Guard 不得把它視為官方 `allowed`。
- 預設：無資料的股票視為 `allowed`，並在報告揭露；若使用者選擇保守做法，改為排除。詳見決策 2。

### 決策鏈

- 與正式流程使用相同 `decision_rules.json`、`decision_policy.json`、Skill 版本與模型參數；每個 run 保存版本雜湊。
- 情緒／共識無歷史核准來源，維持 `unavailable`。
- 每日 20～40 次 `claude -p`。連續執行須處理用量上限，沿用 `--resume`；同一日的失敗、拒絕（rejected）與候選不足都保留在時間軸，不刪除、不重試到成功為止。

### 成交與估值（比賽口徑）

- 決策日 D 的委託在 D 日成交：成交價為 D 日均價（`trade_value / volume_shares`），以整張 1,000 股為單位；無 `trade_value` 時標示替代假設，不以 OHLC 平均冒充。
- 手續費買賣各 0.1425%，賣出證交稅 0.3%，讀 `config/competition_rules.json`；交割 T+2 使用 `TradingCalendar`。
- 部分成交、成交量參與上限與滑價沿用 `ExecutionSimulator` 的既有設定並記錄。
- 以 D 日收盤估值，隔日決策以該日 08:55 的帳戶快照為起點。
- Guard 使用與正式相同的規則（20～30 檔、現金 <25%、個股 10%／2330 25%、產業上限、周轉率）。

### 基準與績效

| 組別 | 說明 |
| --- | --- |
| Agent 全鏈 | 本計畫主體 |
| 固定 25 檔等權 | 相同交易池、成本與 Guard |
| 純動能（不含 LLM） | 使用既有 `MomentumEngine` |
| 0050、加權指數 | 只作報酬參照，需標示資料來源與版本 |

指標：每日 NAV、累計報酬、最大回撤、周轉率、費稅成本、現金比例、持股檔數、Guard 拒絕日、個股與產業貢獻。沿用 B3 比較器，結果固定 `evidence_status=insufficient`。

### 防偏差清單（必須全部揭露於報告）

- 以目前 150 檔名單重播過去：存活者／交易池選擇偏差。
- 模型知識截止日與回測期間的關係：需實查 `claude -p` 實際使用的模型與其知識截止日；若可能已含 8 月資訊，報告需揭露，不可宣稱無洩漏。
- 重建的 `available_at` 是推導值，不等同當時的即時紀錄。
- 單一市況、單次執行；LLM 重跑差異見階段 2。
- 交易狀態假設與未成交假設。

## 階段

### 階段 0：單日重放 2026-08-21（驗證可行性）

工作：
1. 產生 8/21 的資料就緒報告，更正上述行情計數落差。
2. 補抓 8/21 以前所需的重大訊息、營收與財報申報日；每筆記錄 `available_at` 與 `availability_basis`。
3. 實作回測模式 Snapshot（重建 `available_at` 篩選）與 `BacktestRun` 隔離目錄／資料庫。
4. 建立獨立 10 億帳戶，8/21 08:55 建立帳戶快照。
5. 執行完整決策鏈一次，成交後持有至 8/31 收盤，只做估值不調倉。
6. 產生單日重放報告：Agent 呼叫次數、耗時、用量、Guard 結果、委託清單、持有期報酬與相對基準差異。

驗收：
- 同一份保存輸入重建出相同 Snapshot 雜湊與 Decision run 驗證結果。
- Snapshot 內沒有任何 `available_at` 晚於 cutoff 的項目（測試以刻意混入未來資料驗證會被拒絕）。
- 成交與費稅可由手算核對；整張、T+2、賣出稅正確。
- 報告揭露上節全部偏差清單。
- 決策 1～3 已由使用者確認。

### 階段 1：2026-08-03～08-31 逐日調倉

- 21 個交易日連續重放，估計 400～800 次 Agent 呼叫。
- 前置：階段 0 通過；8 月每日 Snapshot 與交易狀態假設完整；用量與時間預算經使用者同意。
- 輸出每日 NAV、與四組基準比較及失敗日時間軸。

### 階段 1 介面：給定日期區間，照比賽規則跑到底

使用者只指定區間，例如 `--start 2026-08-01 --end 2026-08-20`；程式以 `TradingCalendar` 取出區間內的交易日（8/1 為週六，實際第一個決策日為 8/3，共 14 個交易日），不自行補日期。

```text
cli/backtest_replay.py run --start 2026-08-01 --end 2026-08-20 --backtest-id ID [--resume]
cli/backtest_replay.py report --backtest-id ID
```

規則（讀 `config/competition_rules.json`，不在回測程式內另寫一份）：

| 規則 | 回測中的處理 |
| --- | --- |
| 第一個交易日本金 10 億 TWD，空手起算；之後不再注資 | 獨立帳本開帳一次，之後只讀前一日封存狀態 |
| 規則原文（使用者 2026-09-29 提供）：「現金部位每日須小於投資組合淨值之 25%」，嚴格小於、每日適用，首日沒有特例 | 由 `CompetitionGuardV2` 的 `CASH_WEIGHT` 與 `base` 情境強制；首日決策若提案現金 ≥25% 即 rejected，該日記為失敗日，不放寬 |
| 每日持股 20～30 檔、個股 ≤10%（2330 ≤25%）、產業上限、周轉率 | 同一組 Guard，與正式流程一致 |
| 成交後的實際現金比例 | 提案以前一日收盤估算，實際以 D 日均價成交；成交後現金若 ≥25% 或檔數不足，於報告標為 `rule_breach_after_fill`，不改寫成交結果，也不事後補單 |
| 費稅與整張 | 手續費 0.1425%、賣出稅 0.3%、1,000 股單位 |
| 每日提交次數上限、最少成功提交天數 | 回測記錄每日決策次數與成功／失敗日數；正式門檻待主辦方確認 |

報告內容：每日 NAV、現金比例、持股檔數、當日委託與成交、Guard 結果與失敗日；區間報酬、最大回撤、費稅成本與相對基準差異。若區間內任何一天違反上表規則，報告頂端列出違規日，不以平均或最終值掩蓋。

### 階段 2：重跑穩定度

- 同期間重跑 2～3 次，保存全部結果，報告報酬與委託的分散程度；不得只挑最佳一次。
- 加入敏感度：滑價、成交率、交易狀態假設（allowed／排除）。

### 階段 3（選配）：更長期間或規則型歷史回測

- 用兩年官方日線做不含 LLM 的規則策略，校準 ATR 部位與現金姿態等 Policy；仍受歷史交易狀態與交易池偏差限制，需揭露。

## 需使用者確認的決策

1. 日線 `available_at` 推導規則：建議「交易日 18:00 後可得」，次日 08:55 才進 Snapshot。
2. 無歷史交易狀態的股票：建議先視為 `allowed` 並標 `backtest_assumed`；保守做法為排除。
3. 實作位置：建議先放本專案並以路徑與資料庫完全隔離，之後再視需要抽出。
4. 階段 1 的用量預算與可接受的執行時間。
5. 比賽規則原文已取得現金一條（嚴格小於 25%、每日適用，與 `cash_weight_must_be_below` 一致，原文未說明衡量時點）；仍待核對：違反時如何計分、每日成交是否用均價、現金以成交後收盤 NAV 還是日中衡量。

## 風險

- 重建 `available_at` 若過於寬鬆會洩漏未來資料；預設取保守時間，並以測試覆蓋。
- 歷史公告與申報日可能抓不到，導致基本面與事件分析覆蓋不足；缺資料時該日降級而不是補值。
- 模型可能記得回測期間的事件；只能揭露，無法用程式消除。
- 每日 20～40 次呼叫連跑 21 天可能撞用量上限，需分批與續跑。
